This mirrors the SBOM change already shipped in `cli-private` (PR #93, `build: generate SPDX SBOMs for release artifacts via syft`). The agent's release pipeline shares the same GoReleaser-Pro-in-a-builder-image shape, so the change is a near-verbatim port adjusted for the Rust toolchain image.

## Purpose / Big Picture

After this change, every release produced by the agent pipeline also publishes a **Software Bill of Materials (SBOM)** alongside each distributable artifact. An SBOM is a machine-readable inventory of the components and dependencies inside a build artifact; it is increasingly required for supply-chain compliance (SLSA, US EO 14028, EU Cyber Resilience Act, customer security reviews).

Concretely, a release at `github.com/mirurobotics/agent/releases/<tag>` will contain, in addition to the existing tar.gz archives and `.deb` package, one `*.sbom.json` file per archive and per package, in **SPDX-JSON** format, generated by [syft](https://github.com/anchore/syft). GoReleaser uploads these automatically through the existing `release:` stanza — no workflow change is required.

User-visible outcome a human can verify:

1. A snapshot build (`./build/build.sh`) writes `*.sbom.json` files into `build/dist/` next to the archives and `.deb`.
2. Each `*.sbom.json` is valid JSON whose top-level `spdxVersion` field is present (e.g. `"SPDX-2.3"`), confirming SPDX-JSON output.
3. On a real release, those same files appear as downloadable assets on the `mirurobotics/agent` GitHub release.

## Surprises & Discoveries

- syft's GitHub release asset naming differs from GoReleaser's in two ways that matter for the Dockerfile copy-paste. (1) syft's checksums file **embeds the version**: `syft_<VERSION>_checksums.txt` (e.g. `syft_1.46.0_checksums.txt`), NOT a plain `checksums.txt`. (2) syft's tarball uses **lowercase `linux_amd64`** (`syft_<VERSION>_linux_amd64.tar.gz`), NOT GoReleaser's title-cased `Linux_x86_64`. The binary inside the tarball is named `syft`. The `curl -o` target filename must exactly match the name in the checksums file for `sha256sum -c -` to succeed.
  Evidence (collected on host with `SYFT_VERSION=1.46.0`):
      curl ... syft_1.46.0_linux_amd64.tar.gz   -> 200
      curl ... syft_1.46.0_checksums.txt         -> 200
      grep 'syft_1.46.0_linux_amd64.tar.gz$' syft_1.46.0_checksums.txt | sha256sum -c -
        -> syft_1.46.0_linux_amd64.tar.gz: OK
      tar -xzf syft_1.46.0_linux_amd64.tar.gz syft && ./syft version  -> Version: 1.46.0
- The agent's builder image is `rust:1.93.0-bookworm` (Rust + Zig + cargo-zigbuild + GoReleaser), not Go. syft operates on the *built artifacts* (archives, `.deb`), so it is language-agnostic — the install block and `sboms:` stanza are identical in spirit to the cli-private change regardless of the source language.
- The agent's `scripts/lint.sh` chains several optional cargo dev-tools (`cargo-machete`, `cargo-diet`, `cargo-audit`). They were absent from the sandbox initially and were installed to complete the lint signal. None of them is affected by this change (which touches zero Rust code).

## Decision Log

- Decision: Use GoReleaser's native syft-based SBOM support (`sboms:` stanza) rather than a custom build step or separate CI job.
  Rationale: The repo is on GoReleaser Pro v2.13.3 with first-class `sboms:` support. It generates SBOMs at the right point in the pipeline (after archives/packages are built), names them deterministically, and uploads them to the release automatically through the existing `release:` stanza. No workflow edits, no glue scripts. Mirrors the cli-private approach for consistency across Miru release pipelines.
  Date/Author: 2026-06-29.
- Decision: Install `syft` into the builder image (`Dockerfile.builder`) with the same checksum-verified, version-pinned pattern used for GoReleaser, rather than letting GoReleaser download syft on demand.
  Rationale: GoReleaser's default SBOM `cmd` is `syft`; it expects the binary on `PATH`. The builder image is hermetic and offline-friendly by design (everything pinned + checksum-verified). Pinning syft via `ARG SYFT_VERSION` and verifying its SHA256 keeps supply-chain posture consistent with the existing GoReleaser install. The image is published to GHCR by `builder.yml`, so the cost is paid once per toolchain change, not per release.
  Date/Author: 2026-06-29.
- Decision: Produce SPDX-JSON (the GoReleaser/syft default) for both `artifacts: archive` (the tar.gz files) and `artifacts: package` (the `.deb`).
  Rationale: SPDX-JSON is the widely-accepted default and satisfies common compliance asks. Covering both `archive` and `package` ensures every distributable artifact ships with an SBOM. We deliberately do NOT add `artifacts: binary` (the binaries are already inside the archives) or `artifacts: source` (`source.enabled` is `false`).
  Date/Author: 2026-06-29.
- Decision: Do NOT invent a builder image SHA tag in `build/Dockerfile`. Handle the ordering with a comment + a documented post-merge follow-up.
  Rationale: The syft-containing builder image does not exist on GHCR until this PR merges and `builder.yml` runs on `main`. Pre-pinning a guessed SHA would produce a Dockerfile that cannot pull. The existing `a32d4c0` pin is left as-is; the re-pin is called out as a required sequencing step. Until the re-pin lands, `goreleaser release` would run against a builder image without syft and the SBOM step would fail with "syft: command not found".
  Date/Author: 2026-06-29.

## Idempotence and Recovery

- The three file edits are deterministic; re-running them on a clean checkout yields the same final state.
- If `sha256sum -c -` fails with "No such file or directory", the `curl -o` target filename did not match the name in the checksums file — ensure the tarball is saved as exactly `syft_${SYFT_VERSION}_linux_amd64.tar.gz`.
- The post-merge SHA re-pin is reversible: edit the tag back if anything goes wrong; both old and new builder images remain on GHCR.
